# 12. Тестирование

## Принцип

Тестируем то, что легко сломать и дорого отлаживать на телефоне:
- проверку ответов;
- схемы контента;
- миграции БД;
- планировщик SRS;
- ссылки текста на словарь;
- офлайн-сценарии.

Не гонимся за 100% покрытием UI.

## Уровни

### Unit
- Проверка ответов всех типов упражнений.
- Нормализация строк.
- Валидация course pack (Zod).
- Расчёт due/интервалов FSRS с фиксированным `now`.
- Утилиты каны/фуриганы.
- Парсинг/маппинг словарных записей.

### Component
- Exercise-компоненты: выбор, пропуск, порядок.
- Состояния обратной связи.
- Нижний лист словаря.
- Токены/фуригана.

### Integration
- Репозитории `user.db` на временной БД.
- Миграции: старая схема → новая, данные на месте.
- Поиск по тестовой `dictionary-ja-ru.db`.
- Добавление карточки + дедупликация.
- Транзакция «карточка + review log».

### E2E / ручное
- Полный проход урока на Android-телефоне.
- Авиарежим.
- Перезапуск приложения.
- Тап по слову в тексте → статья → колода.
- Повторение.

E2E-инструмент (Maestro) — позже; в MVP достаточно ручного чек-листа.

## Валидация контента

`scripts/validate-content.ts` должен проверять:
- Zod-схемы;
- уникальность ID;
- корректность `correctIndex`/`correctOrder`;
- наличие объяснений;
- покрытие текста токенами;
- ссылки `entryIds` на словарь;
- соответствие манифеста и файлов;
- отсутствие дубликатов.

Валидация запускается локально и в CI. Ошибка контента не должна доходить до телефона.

## Тестирование БД

- Каждая миграция — отдельный тест.
- Проверка `PRAGMA user_version`.
- Проверка, что старые данные не потеряны.
- Проверка foreign keys.
- Проверка, что `dictionary-ja-ru.db` открывается read-only и не мутируется.
- Тестовая БД — во временном каталоге, не в рабочей.

### Замечание
`expo-sqlite` в тестах Node может требовать мока/адаптера. Чистые SQL-функции и репозитории проектировать так, чтобы их можно было тестировать на `better-sqlite3`/`node:sqlite` или на временной БД. Не тащить нативный модуль в runtime.

## Тестирование SRS

- Фиксированный `now`.
- Фикстуры состояний: new, learning, review, relearning.
- Для каждой оценки — ожидаемые `state`, `due`, `stability`, `difficulty`.
- Проверка, что `review_log` соответствует пересчёту.
- Проверка, что повторное добавление не создаёт дубликат.
- Проверка границы дня/часового пояса.

## Офлайн-тесты

- Включить авиарежим.
- Пройти урок, открыть словарь, добавить слово, повторить.
- Убедиться, что нет сетевых запросов и «вечных» загрузок.
- Перезапустить приложение и проверить данные.

## Устройства

- Основное: Android-телефон пользователя, Expo Go.
- Позже: development build, разные размеры экрана, Android-версии.
- iOS — после появления в scope.

## CI

Позже, на GitHub Actions:
1. `npm ci`
2. `lint`
3. `typecheck`
4. `test:content`
5. `content:validate`
6. при необходимости — сборка словаря/ассетов.

Текущие проверки: `npm run typecheck`, `npm run test:content`, `npm run content:validate`, `npx expo-doctor`, `npx expo export --platform android`. Lint и полноценный UI-test suite появятся отдельными шагами; держать `AGENTS.md` в актуальном состоянии.

## Ручной чек-лист перед сдачей этапа

- [ ] Приложение запускается на телефоне.
- [ ] Нет сети — основные сценарии работают.
- [ ] Перезапуск сохраняет прогресс.
- [ ] Ошибки контента понятны.
- [ ] Ошибки БД не удаляют данные.
- [ ] Тексты/словарь/карточки не ломают друг друга.
- [ ] Лицензии и атрибуция доступны.
- [ ] Размер и скорость приемлемы.
- [ ] Новый урок добавляется без правки UI.

## Тестовые данные

- Маленькие фикстуры, без copyrighted контента.
- Для словаря — минимальная тестовая БД с 5–10 статьями.
- Для текстов — короткий текст с токенами.
- Для SRS — набор карточек в разных состояниях.
