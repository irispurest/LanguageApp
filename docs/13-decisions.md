# 13. Принятые решения (ADR)

Формат: контекст → решение → последствия. Статусы: `Accepted`, `Superseded`, `Proposed`.

## ADR-001. Одно универсальное приложение + course packs

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** нужно выбрать между единым приложением с конструктором курсов и отдельным приложением под японский с шаблоном для других языков.

**Решение:** одно приложение; универсальное ядро, языковые адаптеры, course packs. Японский — первый language pack.

**Последствия:**
- один кодбейс и общий SRS/словарь/UI;
- выше риск преждевременных абстракций;
- визуальный конструктор курсов откладывается;
- второй язык проверяется небольшим паком, а не полноценным курсом.

## ADR-002. Android + Expo Go first, iOS отложен

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** разработка на Windows, есть Android-телефон и Expo Go.

**Решение:** первый этап — только Android через Expo Go. iOS не входит в scope, пока не появится отдельное решение.

**Последствия:**
- не нужны JDK/Android Studio для первого запуска;
- iOS-специфичные проверки и EAS/TestFlight откладываются;
- Expo-код остаётся кроссплатформенным, но iOS не тестируется.

## ADR-003. Первый вертикальный срез — грамматика + тесты

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** пользователь хочет проверить приложение и курс; уровень N5+.

**Решение:** первый срез — 1–2 грамматических урока с тремя типами упражнений и офлайн-прогрессом. SRS, словарь и тексты — следующие этапы.

**Последствия:**
- проверяется контент/упражнения/БД без тяжёлого словаря;
- схема данных сразу проектируется под словарь/SRS/тексты;
- словарь и SRS не блокируют первый запуск.

## ADR-004. Offline-first, без бэкенда и аккаунтов

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** приложение должно работать в поездке и на перерывах; пользователь не хочет обязательный онлайн.

**Решение:** все основные сценарии офлайн; нет логина, облака, аналитики. Бэкенд — только позже и только на C#/.NET при реальной необходимости.

**Последствия:**
- данные локальны;
- нужен экспорт/бэкап;
- синхронизация не входит в MVP;
- загрузка контента позже должна быть явной и необязательной.

## ADR-005. Стек: Expo + TypeScript + Expo Router + expo-sqlite

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** нужен быстрый старт, обучение React Native и работа в Expo Go.

**Решение:** Expo SDK (последний стабильный), React Native, TypeScript strict, Expo Router, `expo-sqlite`.

**Последствия:**
- минимум нативной конфигурации;
- SQLite и FTS5 доступны в Expo Go;
- версии фиксируются в `package.json`;
- canary/next SDK не используем.

## ADR-006. Без ORM в MVP

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** схема небольшая, пользователь учится; ORM добавляет слой и кодогенерацию.

**Решение:** явные SQL-запросы, типизированные репозитории, миграции вручную.

**Последствия:**
- прозрачность и контроль;
- больше ручного SQL;
- Drizzle можно рассмотреть позже, если схема вырастет.

## ADR-007. Две БД: user.db и dictionary-ja-ru.db

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** словарь большой и обновляемый, прогресс — маленький и критичный.

**Решение:** `user.db` read/write; `dictionary-ja-ru.db` read-only asset.

**Последствия:**
- обновление словаря не трогает прогресс;
- проще миграции пользовательских данных;
- приложение никогда не пишет в словарь;
- карточки хранят снимки, а не только ссылки.

## ADR-008. Контент — JSON, не таблицы БД

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** уроки небольшие, их нужно часто редактировать.

**Решение:** course packs — JSON + Zod; прогресс ссылается на стабильные ID.

**Последствия:**
- контент можно валидировать отдельно;
- меньше миграций;
- нужен generated index для Metro;
- большие паки позже можно кэшировать/индексировать.

## ADR-009. SRS — FSRS через ts-fsrs

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** нужен современный алгоритм без собственных формул.

**Решение:** `ts-fsrs` v6+, FSRS по умолчанию; версия библиотеки фиксируется.

**Последствия:**
- планировщик тестируется детерминированно;
- журнал ответов позволит оптимизацию позже;
- нельзя менять алгоритм без миграции/пересчёта.

## ADR-010. Словарь — JMdict-rus, common-only на старте

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** нужен офлайн-японско-русский словарь с открытой лицензией.

**Решение:** `jmdict-rus` из `jmdict-simplified`; стартовый бандл — common-only (~18.5k статей, ~10.1 МБ JSON). Полный словарь — отдельный пак позже.

**Последствия:**
- русские значения без собственного перевода;
- лицензия CC BY-SA 4.0, атрибуция и обновление обязательны;
- размер контролируем;
- возможны пропуски слов/глоссов — нужен fallback.

## ADR-011. Тексты токенизируются на этапе сборки

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** японский без пробелов; runtime-токенизатор тяжёлый.

**Решение:** хранить токены (surface/lemma/reading/entryIds) в JSON; на телефоне только рендер и lookup.

**Последствия:**
- быстрый и предсказуемый ридер;
- нужен пайплайн сборки и валидация;
- свободный ввод/произвольные тексты ограничены;
- проще связать токены со словарём.

## ADR-012. Русский UI first, i18n-ready

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** пользователь русскоязычный; словарь русский.

**Решение:** интерфейс и переводы на русском; строки в одном слое, без хардкода в JSX.

**Последствия:**
- проще пользователю;
- позже можно добавить второй язык UI;
- контент/строки не смешивать с логикой.

## ADR-013. Три типа упражнений, без free-text в MVP

**Дата:** 2026-11-21. **Статус:** Accepted.

**Решение:** multiple choice, cloze из банка, ordering. Свободный ввод по-японски — позже.

**Последствия:**
- предсказуемая проверка;
- не зависим от IME;
- меньше типов — быстрее стабилизировать движок.

## ADR-014. Без визуального конструктора курсов в MVP

**Дата:** 2026-11-21. **Статус:** Accepted.

**Решение:** JSON + валидатор + ручное редактирование. Конструктор — после стабилизации формата.

**Последствия:**
- меньше scope;
- авторство контента менее удобно;
- формат можно менять без UI-legacy.

## ADR-015. Без кастомных нативных модулей в MVP

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** старт в Expo Go без Android Studio/JDK.

**Решение:** использовать только модули, доступные в Expo Go. Всё нативное — после development build.

**Последствия:**
- быстрый цикл разработки;
- некоторые функции (SQLCipher, кастомные ML-модули) откладываются;
- перед добавлением библиотеки проверять Expo Go-совместимость.

## ADR-016. Стабильные ID и epoch ms

**Дата:** 2026-11-21. **Статус:** Accepted.

**Решение:** ID контента/карточек — стабильные строки; время — epoch ms UTC; локальная граница дня — только для отображения.

**Последствия:**
- прогресс переживает правки контента;
- проще сравнивать время/планировать;
- переименование ID запрещено.

## ADR-017. Словарная БД генерируется, не коммитится

**Дата:** 2026-11-21. **Статус:** Accepted.

**Решение:** raw JSON и `dictionary-ja-ru.db` — generated assets; в репозитории только скрипт, версия и checksum.

**Последствия:**
- репозиторий лёгкий;
- нужен шаг сборки перед запуском/релизом;
- воспроизводимость через pinned release.

## ADR-018. Лицензия словаря и экран «Источники»

**Дата:** 2026-11-21. **Статус:** Accepted.

**Решение:** JMdict/EDRDG и `jmdict-simplified` атрибутируются в приложении; лицензия CC BY-SA 4.0; процедура обновления описана.

**Последствия:**
- нельзя «забыть» про лицензию;
- производная БД под той же лицензией;
- обновление словаря — регулярная операция.

## ADR-019. Порядок: словарь → SRS → тексты

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** тексты должны сразу вести в словарь и колоду.

**Решение:** после грамматики — словарь и хранение колоды, затем SRS, затем ридер.

**Последствия:**
- текст сразу проверяет полную связку;
- SRS не строится на пустом месте;
- словарь можно тестировать отдельно.

## ADR-020. Первый курс — знакомые N5-темы

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** пользователь уровня N5+ хочет проверять приложение, а не учить новое.

**Решение:** первый курс собирается из знакомых N5-тем; приоритет — покрытие типов упражнений и UX.

**Последствия:**
- проще проверять корректность контента;
- меньше риск, что ошибка в приложении маскируется незнанием темы;
- после стабилизации можно добавлять новые темы.

## ADR-021. Первый каркас — blank-typescript, Expo Router отдельным шагом

**Дата:** 2026-11-21. **Статус:** Accepted; реализовано в шаге 2.

**Контекст:** нужно сначала увидеть минимальный React Native-проект, объяснить экраны/кнопки/состояние и не смешивать это с навигацией.

**Решение:** старт с `blank-typescript` и одним `App.tsx`; Expo Router, два пустых экрана и переходы добавляются следующим шагом.

**Последствия:**
- временно нет файлового роутера и вкладок;
- структура `app/` появится после добавления Router;
- нельзя строить фичи поверх `App.tsx`, если они требуют навигации;
- шаг хорошо подходит для обучения: видно разницу между одним компонентом и маршрутами.

## ADR-022. JavaScript tabs + root Stack; route → feature screen

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** нужны основные разделы приложения, единый стиль таб-бара и один stack-переход для служебного экрана.

**Решение:** использовать JavaScript `Tabs` из Expo Router для пяти разделов и root `Stack` для «О приложении». Route-файлы в `app/` тонкие и только рендерят feature-экраны; UI-компоненты — в `src/ui/`, строки — в `src/i18n/`.

**Последствия:**
- единый стиль табов и предсказуемая навигация;
- feature-экраны можно тестировать/менять без файлового роутера;
- native tabs не используем, пока нет отдельной причины;
- переход на native tabs позже локализован в `app/(tabs)/_layout.tsx`.

## ADR-023. React 19.3.0 + react-dom 19.3.0; expo-font напрямую

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** Expo-шаблон фиксирует React `19.3.0`. Expo Router подтянул `react-dom@19.3.1`, который требует React `^19.3.1`; `npm install expo-font` падал с ERESOLVE. `expo-font` нужен `@expo/vector-icons` и проверяется `expo-doctor`.

**Решение:** оставить React `19.3.0`, зафиксировать `react-dom@19.3.0`, добавить `expo-font@58.0.12` прямой зависимостью. Не использовать `--force`/`--legacy-peer-deps` для обхода.

**Последствия:**
- `npm install` и `expo-doctor` проходят без хаков;
- нельзя обновлять `react`/`react-dom` по отдельности;
- при обновлении Expo SDK проверить пару версий заново.

## ADR-024. Пять вкладок; повторение — режим, не таб

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** нужна отдельная Главная с обзором и настройками, чистый список уроков и справочники.

**Решение:** пять табов — Главная, Курс, Словарь, Грамматика, Тексты. Повторение — stack-экран/режим, запускается с Главной, из урока, в конце раздела и из словаря. Настройки — stack с Главной.

**Последствия:**
- Главная отвечает за «что делать сейчас», Курс — только за структуру уроков;
- отдельного урока/таба повторения нет;
- review-режим переиспользуется из разных мест;
- текущий app shell нужно перестроить под эту схему.

## ADR-025. Один курс «Японский» с уровнями N5/N4/N3

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** пользователь хочет несколько уровней и непрерывный прогресс.

**Решение:** один course pack с уровнями; уровень → разделы → упорядоченные уроки. Новый урок вставляется ID в нужный раздел.

**Последствия:**
- один курс в главной вкладке;
- уровни можно добавлять постепенно;
- ID уроков стабильны, порядок задаётся массивом раздела;
- отдельные паки на уровень — возможное будущее, не MVP.

## ADR-026. Один список с фильтрами; личный словарь по умолчанию

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** два отдельных списка «всё/пройдено» дублируют UI и данные.

**Решение:** один каталог + один список с фильтрами «Все/Пройдено» и бейджами. В словаре по умолчанию открывается личный словарь; поиск идёт по глобальному JMdict, личные результаты помечаются. Полный глобальный словарь не рендерится списком.

**Последствия:**
- прогресс хранится отдельно от контента;
- меньше дублирования экранов;
- для словаря нужен поиск-first UI;
- группировка личного словаря по уровню и сортировка по времени добавления.

## ADR-027. Авторство уроков — JSON + CLI, без in-app редактора

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** уроки — данные; in-app редактор — отдельный большой продукт.

**Решение:** CLI создаёт шаблон урока и вставляет ID в раздел; JSON валидируется Zod; in-app редактор не делаем в ближайшее время.

**Последствия:**
- быстрый и контролируемый авторский процесс;
- нужен CLI и валидатор;
- пользовательские уроки/импорт — будущее.

## ADR-028. Zod для валидации контента

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** JSON-контент нужно проверять в рантайме/на сборке, а TypeScript-типы не существуют в рантайме.

**Решение:** Zod-схемы для course pack, уровней, разделов, уроков, упражнений, слов и текстов; типы выводятся через `z.infer`; валидация на этапе сборки/CI и при импорте.

**Последствия:**
- ошибки контента ловятся до телефона;
- схема — единый источник типа и валидации;
- нужно версионировать схемы;
- Zod не используется для валидации каждого внутреннего вызова.

## ADR-029. Повторение после каждого урока с лимитом

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** повторение только в конце раздела — слишком редко, вперемешку — сложно и может ломать поток; отдельный урок повторения смешивает статический контент и динамическую очередь.

**Решение:** после каждого урока — опциональное повторение до 10 слов (`after_lesson`, `maxWords: 10`). Политика хранится в разделе, лимит настраиваемый. Глобальная кнопка «Повторить» — на Главной.

**Последствия:**
- короткая сессия после урока;
- due-очередь не попадает в статический контент;
- `interleaved`/`section_end` можно добавить позже;
- 10 — стартовое значение, не окончательная настройка.

## ADR-030. Личный словарь сортируется, но не группируется по уровню

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** уровень слова не гарантирован для всех записей JMdict и ручных слов.

**Решение:** личный словарь сортируется по времени добавления / прогрессу / алфавиту; группировка по уровню не используется.

**Последствия:**
- нет ложной группировки;
- проще UI и запросы;
- уровень может отображаться как метаданные, если известен;
- JLPT-уровень можно добавить отдельным источником позже.

## ADR-031. Общий раздел справочников — «Библиотека»

**Дата:** 2026-11-21. **Статус:** Accepted.

**Решение:** словарь, грамматика и тексты — «Библиотека»; вкладки остаются с собственными названиями.

**Последствия:** в текстах/навигации можно использовать «Библиотека» как общий термин, не переименовывая вкладки.

## ADR-032. Палитра: розово-красный + персиковый

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** пользователь хочет красноватый/розовый ключевой цвет; персиковый — как альтернатива; позже попросил сделать акцент ярче и пастельнее.

**Решение:** основной accent — пастельный розово-красный `#D96B80`; мягкий фон/акцент — персиковый `#FBE3DF`; для мелкого текста/активных табов — `accentStrong #A63D56`; текст на пастельном primary — тёмный `#3A2027`.

**Последствия:**
- пастельный primary используется с тёмным текстом, а не с белым — иначе падает контраст;
- для мелких подписей остаётся более насыщенный `accentStrong`;
- все цвета — только через `src/ui/theme.ts`;
- палитру можно заменить одним изменением токенов.

## ADR-033. Курсы по языковым парам; UI-язык из системы

**Дата:** 2026-11-21. **Статус:** Accepted.

**Контекст:** нужно решить, делать один курс с локализацией внутри или отдельные курсы для русскоязычных/англоязычных. Пользователь хочет курс под конкретную пару языков и UI-язык из системы.

**Решение:**
- Курс — конкретная пара `targetLanguage-sourceLanguage`, сейчас `ja-ru`.
- ID контента включают `courseId`: `ja-ru-n5-wa-ga`.
- Контент лежит в `content/ja-ru/`; словарь — `dictionary-ja-ru.db`.
- UI-язык определяется системным locale с fallback `ru`; поддерживается только `ru`, английский UI позже.
- UI-язык не хранится в course pack и не обязан совпадать с `sourceLanguage` контента.
- Второй язык — отдельный course pack (`ja-en`), а не поля-переводы в одном курсе.

**Последствия:**
- проще контент и валидация;
- нет fallback-логики переводов внутри урока;
- прогресс и карточки привязаны к курсу;
- японские примеры/тексты можно вынести в shared-слой позже, когда появится второй курс.
